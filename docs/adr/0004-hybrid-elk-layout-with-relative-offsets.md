# 0004: ELK.js 階層自動レイアウトと手動相対オフセット永続化のハイブリッド方式

- **Status**: Accepted
- **Date**: 2026-11-26

## Context

Structurizr DSL の `model` には座標情報が含まれないため、単一 2D 空間入れ子モデル（[ADR 0001](./0001-spatial-nesting-and-screen-space-lod.md)）を描画するには自動レイアウトが必須となる。

一方で、地図アプリ的な探索では「このシステムは左上、認証は北側」といった**空間記憶（Spatial Memory）**が重要になる。完全自動レイアウトのみだとユーザーが好みの位置へ調整できず、逆に完全手動配置を強制すると初期構築のコストが高すぎる。

## Decision

1. **初回および標準配置には `elkjs` の複合グラフ（Compound Graph）レイアウト（`INCLUDE_CHILDREN` + `layered`）を採用し、同一モデルに対して決定的な座標を算出する**。
   - 子を持つ要素には展開時のヘッダーラベル領域と周囲パディングを確保する。
2. **ユーザーによる手動配置調整は、絶対座標ではなく「自動レイアウト座標からの相対オフセット差分 (`Record<ElementId, { dx: number; dy: number }>`)」として `localStorage` に永続化し、レイアウト後に非破壊適用する**。
   - 通常のドラッグは地図パンに専念させ、配置調整は専用モードまたは `Alt + ドラッグ` に限定する。
   - 親ノードの移動時は子孫を追従させ、子ノードが親枠外へ出た場合は親のバウンディングボックスを自動拡張する。

## Alternatives Considered

- **完全自動レイアウトのみ**:
  - 実装は単純だが、ユーザーが好みの地理的配置へ微調整して空間記憶を定着させる体験が作れないため不採用。
- **絶対座標のスナップショット保存**:
  - DSL に要素が追加・削除された際に既存座標との整合が崩れやすく、新規追加ノードの配置計算と相性が悪いため不採用。
- **力学モデル（Force-directed）レイアウト**:
  - 入れ子境界の厳密な包含表現や階層的なデータフローの視認性が落ち、再計算ごとの安定性も低いため不採用。

## Consequences

- **メリット**:
  - 座標ゼロの `.dsl` を読み込んだ直後から整った地図が表示され、必要な箇所だけ微調整して記憶できる。
  - 相対オフセット方式のため、DSL に別要素が追加されても調整済みノードの意図を壊しにくく、個別／一括リセットも容易。
- **トレードオフ・制約**:
  - `elkjs` はバンドルサイズが比較的大きいため、非同期実行で UI ブロックを避ける必要がある。
  - 親子バウンディングボックスの再計算とオフセット適用ロジックの単体テストが必須になる。
