# 0003: カスタム HTML5 Canvas 2D レンダラーの採用とコア／UIの厳格な責務分離

- **Status**: Accepted
- **Date**: 2026-11-26

## Context

c4-zoom の中核体験である「連続セマンティック・ズーム（`0.04x 〜 12x`）」では、ズーム倍率の変化に応じて毎フレーム（60fps）以下を滑らかに制御する必要がある：
- 親ノードの背景不透明度・枠線・ヘッダー位置の連続補間
- ズームしても画面上で読みやすい文字サイズ・枠線太さの正規化
- 数百ノード・多数エッジにおけるビューポートカリングとエッジラベル衝突回避
- 慣性パン・放物線 Fly-to カメラ補間・トレース時のパルスアニメーション

また、将来的にこの地図エンジンをローカル CLI ビューアや VS Code 拡張へ展開する可能性も見据えたい。

## Decision

1. **地図キャンバスの描画エンジンとして「カスタム HTML5 Canvas 2D（HiDPI 対応）」を採用し、操作パネルのみ React フローティングオーバーレイで重ねるハイブリッド構成とする**。
2. **ディレクトリおよび依存関係レベルで `src/core/` と `src/ui/` を厳格に分離する**。
   - `src/core/`（`model`, `dsl`, `layout`, `camera`, `lod`, `renderer`）には **React や UI 状態管理への依存を一切持ち込まない**純粋な TypeScript モジュールとする。
   - 毎フレームの描画ループ（`requestAnimationFrame`）は React の再レンダリングサイクルから切り離して駆動する。

## Alternatives Considered

- **SVG / DOM ベース（React Flow 等のグラフライブラリ拡張）**:
  - DOM 要素でリッチなカードを書きやすい一方、多段ネストされた空間入れ子で連続 LOD や極端なスケール変化を行うと、文字サイズや枠線制御でライブラリの前提と衝突しやすく、ノード増加時の描画性能も劣化しやすいため不採用。
- **WebGL（PixiJS / Three.js 等）**:
  - 数万ノード規模では圧倒的に高速だが、日本語を含む高品質なタイポグラフィ描画（MSDF フォント生成等）や角丸カード・繊細なドロップシャドウの実装・保守コストが高いため、数百〜千ノード規模を主戦場とする本アプリではオーバースペックと判断し不採用。

## Consequences

- **メリット**:
  - 地図アプリ固有の描画ルール（画面サイズ一定ラベル、smoothstep クロスフェード、ラベル衝突回避、Retina シャープ描画）を 100% 思い通りに 60fps で制御できる。
  - `src/core/` が純粋 TypeScript であるため、Vitest による高速なヘッドレス単体テストが書きやすく、将来のプラットフォーム展開も容易。
- **トレードオフ・注意点**:
  - ヒットテスト（要素・ベジェ曲線のクリック/ホバー判定）やテキスト折り返し・省略（ellipsis）を自前実装する必要がある。
  - Canvas 内部は DOM ツリーを持たないため、キーボードショートカット（`⌘K`, `0`, `1/2/3`, `Esc`）やフローティング UI（検索・インスペクタ）でアクセシビリティと操作性を補完する。
