# 0001: 単一2D空間入れ子モデルと画面占有サイズ基準の連続 LOD

- **Status**: Accepted
- **Date**: 2026-11-26

## Context

本アプリは「地図アプリのように 1 枚の連続空間を移動・ズームイン／ズームアウトしながら C4 アーキテクチャを探索する」体験を目的としている（プロダクト方針・Non-Goals は [docs/design.md](../design.md) を参照）。

既存の C4 ビューア（Structurizr UI / LikeC4 等）は Context 図・Container 図・Component 図を独立した別ビューとして描画し、クリックで画面遷移する構造を採っている。一方、本アプリではシステム間を横パンで移動しながら隣接するシステム内部を同時に比較できる空間構造と、規模の異なるシステムが混在しても破綻しない詳細度制御（LOD: Level of Detail）の仕組みが必要になる。

## Decision

1. **空間モデルとして「単一 2D 空間入れ子モデル（Compound Spatial Nesting）」を採用する**。
   - `System ⊃ Container ⊃ Component` を 1 つの共通ワールド座標系に入れ子配置し、別ビューへのページ切り替えを行わない。
2. **LOD 判定にはグローバルなズーム倍率ではなく、各要素の「スクリーン上の見かけサイズ (`min(width * zoom, height * zoom)`)」を用いる**。
   - `140px 〜 260px` の帯域で `smoothstep` により `detailAlpha ∈ [0, 1]` を連続算出し、ランドマーク表示（Collapsed）から地区枠＋子要素展開（Expanded）へ滑らかに遷移させる。

## Alternatives Considered

- **階層ダイブ型（個別ビュー間のアニメーション遷移）**:
  - 各階層のレイアウトを独立計算できる利点はあるが、異なるシステムの中身を並べて比較したり、ズームしたまま隣へ横パンする空間記憶（Spatial Memory）が成立しないため不採用。
- **グローバルズーム倍率による一律 LOD 切替**:
  - 実装は単純だが、コンテナ数が多い巨大システムと小さい外部システムが同居した際、「巨大システムは十分大きいのにまだ閉じたまま」「小さいシステムは文字が潰れているのに開いてしまう」問題が起きるため不採用。

## Consequences

- **メリット**:
  - 画面左側の大きなシステムは L2/L3 が展開され、右側の小さな外部システムは L1 ランドマークのままという自然な多階層表示が成立する。
  - ズーム操作とパン操作だけで全階層をシームレスに行き来できる。
- **トレードオフ・制約**:
  - 階層レイアウト計算が複合グラフ（Compound Graph）前提になる（[ADR 0004](./0004-hybrid-elk-layout-with-relative-offsets.md)）。
  - 展開状態がノードごとに混在するため、関係線も可視状態に応じた動的アンカー射影が必要になる（[ADR 0005](./0005-dynamic-edge-rollup-by-visible-anchor.md)）。
